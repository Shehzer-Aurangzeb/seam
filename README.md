# Seam

Catches backend API changes that break your frontend — and stays quiet about the ones that don't.

A seam is where two things are joined, and the first place they tear. This watches the seam between a
frontend and the backends it calls.

## The problem

Every OpenAPI diffing tool answers the same question: *did the spec change in a breaking way?* That's
a property of the spec alone, so every consumer gets the same alert.

```
- internalAuditFlag removed from GET /orders/{id}   ← BREAKING, says every spec differ
```

Except nothing in your frontend ever read `internalAuditFlag`. That alert is noise, and after enough
of them the channel gets muted — including the one alert that mattered.

Seam asks a narrower question: *did the spec change in a way that breaks **this** frontend, given what
it actually reads?* It scans the frontend once to learn which response fields and request headers are
genuinely consumed, then judges every subsequent spec change against that.

```
~ MODIFIED GET /orders/{id}
      response field 'total' type changed "number"→"string"
      header 'x-region' became required and the frontend does not send it
IGNORE
  ~ MODIFIED POST /orders/query — response field 'items[].warehouseCode' is not read by the frontend
```

Same spec diff. Three findings instead of forty.

### Why not `oasdiff` or `openapi-typescript`?

Both are good, and neither covers this.

- **`oasdiff`** diffs two specs and classifies breaking changes. Better at that than Seam will ever be
  — but it has no model of what any particular consumer reads, so it can't stay quiet.
- **`openapi-typescript`** generates types, and `tsc` then catches removed response fields you use.
  Excellent, if your frontend already consumes generated types. Retrofitting them across a mature
  codebase is a migration; Seam reads the code as it is.
- **Neither sees headers.** A newly-required `x-region` that your axios client doesn't send is a
  runtime 400. It isn't in the type surface, and a spec differ can't know whether *you* send it.
- **Neither knows where to file it.** Five backends — two of them third-party with no repo — and the
  question is which upstream broke you.

## How it works

**LLM at the edges, deterministic core.**

`init` reads the frontend with Claude and writes a config: which routes are called, which headers the
shared client sends, and which response paths get read. That's the only LLM step.

`check` fetches the OpenAPI spec, diffs it against the last snapshot, and classifies every change
against the config. No LLM in detection or classification — the same inputs always produce the same
verdicts. Claude is called once more at the end, purely to phrase the findings for humans, and the
run works fine without it.

## Quick start

```bash
pnpm install
echo 'ANTHROPIC_API_KEY=sk-ant-...' > .env

# Scan the frontend. Point it at the directory where API calls live.
pnpm init ../my-frontend/src

# Fill in specUrl for each backend in config/backends.json, then:
pnpm check                                        # one config, or pick interactively
pnpm check driftcheck.platform-service-url.config.json

# "Do the frontend and the spec agree right now?" — one spec, no snapshot.
pnpm dev verify driftcheck.platform-service-url.config.json
```

The first `check` on a backend captures a baseline and reports nothing. Every run after that compares
against it.

## `check` vs `verify`

`check` is a **changelog**: two specs, "what did the backend change since last run?" It needs a
snapshot, and it cannot see your frontend being *fixed*, because fixing a frontend doesn't touch the
spec.

`verify` is a **checklist**: one spec, "does everything the frontend uses still exist?" No snapshot,
no memory of previous runs — run it a hundred times and it answers the same. That is what lets an
automatically-opened issue close itself once the disagreement is gone.

Both exit `2` on a breaking finding, `1` only when the tool itself failed.

## Configuration

### `config/backends.json`

Where the backend's spec lives. One entry per backend, typed in once.

```json
{
  "platform-service-url": {
    "specUrl": "https://platform.internal/docs-json",
    "basePath": "/api/v1"
  }
}
```

Keyed off the config filename, which `init` derives from the base-URL environment variable in your
code (`PLATFORM_SERVICE_URL` → `platform-service-url`). That key is stable, so **deleting every config
file and re-running `init` never loses these values** — the whole reason this file is separate.

`basePath` is the prefix the spec carries but the frontend's base URL hides. Leave it `""` if the spec
paths match what the code calls.

### `config/driftcheck.<backend>.config.json`

What the frontend consumes. Generated by `init`, and the source of truth for everything Seam ignores.

```json
{
  "globalHeaders": ["authorization", "x-tenant-id"],
  "consumes": [
    {
      "method": "GET",
      "path": "/orders/{id}",
      "headers": ["x-idempotency-key"],
      "responseFields": ["customer.email", "items[].sku", "total"]
    }
  ]
}
```

| Field | Meaning when present | Meaning when absent |
|---|---|---|
| `globalHeaders` | headers the shared client puts on every call | monitor every header |
| `headers` | what this call site adds on top | — |
| `responseFields` | the only response paths that can produce a finding | monitor the whole response |
| `requestFields` | parsed and carried, but no rule reads it yet | — |

**Absent means "we never looked, so monitor everything."** That keeps a config written before this
existed behaving conservatively. An *empty* list is treated the same way, deliberately: a model that
means to omit a key often emits `[]`, and a config that quietly stops reporting is worse than one that
over-reports.

Header names are lowercase everywhere — HTTP header names are case-insensitive, and comparing them any
other way invents drift.

Nested paths use dots, array elements use `[]`: `profile.firstName`, `items[].sku`. Array-ness never
decides consumption, so `items[].sku` and `items.sku` match the same change.

## Severity

| | |
|---|---|
| **breaking** | a field you read was removed, renamed or retyped; a header you don't send became required; a header you do send narrowed its accepted values |
| **relevant** | worth knowing — a field you read is now optional, a header you send is deprecated, a new operation appeared |
| **ignore** | changes to anything you don't touch, and cosmetic edits to descriptions and examples |

A change to a route absent from `consumes` is never reported at all.

## Status

Working: `init` (local directory or a GitHub repo it never clones), `check`, `verify`, multi-backend
configs, header resolution, request- and response-field scoping.

Not built yet:

- **Retype detection in `verify`.** `check` catches retypes; `verify` can't, because the config
  records which fields are read, not what type they were. Removal is what auto-close needs, and that
  works.
- **The loop.** A scheduled `verify` that opens a GitHub issue per finding and closes it when the
  finding disappears.

## Tests

```bash
pnpm test
```

Runs the unit suites and `tsc`. No framework — plain `node:assert` files that exit non-zero on
failure.
